# Reasons behind the working agreement

Not loaded into sessions. Section numbers match `RULES.md`.

| Section | Problem it prevents |
|---|---|
| 1. Claims and evidence | Fluent text sounds equally sure whether the writer measured something or assumed it. Requiring fresh evidence makes the two distinguishable, and stating the scope stops a partial count from passing as the whole. |
| 2. Actions that need care | Most data accidents are reversible if someone knew the reach beforehand and kept the old values. Permission tied to a named list keeps a small cleanup from becoming a large one. |
| 3. Limits that always hold | Automation repeats a mistake at machine speed. A few outcomes cannot be undone, so they are listed apart from ordinary rules and checked by programs as well as by instructions. |
| 4. Several sessions at once | Sessions on one computer share working copies and deployment targets. Claims, locks and handoffs keep one session from overwriting another or releasing at the same moment. An independent reviewer sees what the author overlooked. |
| 5. Writing code | Small, focused changes can be reviewed and reverted. A check that is able to fail is the only proof that code does what was intended. |
| 6. Database schema | When the repository and the database disagree, the next person builds on the wrong one. Recording and applying each change together keeps them in step. |
| 7. Tokens and plan limits | Everything in context is paid for again on every call, and a plan limit stops work without warning. Reading less and checking the meter first avoid both. |
| 8. Keeping state | Context is temporary. Files survive compaction, restarts and crashes. |
| 9. Installing things | Poisoned releases are usually discovered and withdrawn within days, so waiting avoids most of them. Extensions run with the user's access, so they are examined before they are switched on. |
| 10. Completing a request | Unfinished work has to be reconstructed by whoever picks it up. Repeating a refused call wastes effort and weakens the refusal. A short, predictable ending lets the user act without rereading the session. |
